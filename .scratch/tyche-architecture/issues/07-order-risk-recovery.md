## Question

手工指令和自动策略共享账户时，订单、持仓归属和风控应如何协调？对提交结果未知、部分成交、撤单竞争、重复回报、重连及重启逐项定义可观察行为。明确订单状态的权威来源、恢复前的交易限制，以及停止策略、撤销挂单和紧急操作的不同含义。

沿用 [工作台决议](05-workbench-workflow.md) 的价格梯点击、监控面板操作、固定账户/策略对象、显式重新启用与状态失效展示要求；前端交互限制不能替代后台的指令校验、风控及恢复前置条件。

结合 [Binance 首版范围](12-binance-scope.md) 与 [衍生品能力研究](22-binance-crypto-market-making.md)，明确期权卖出开仓的准入检查，以及 MMP、Options/Futures 倒计时撤单哪些属于策略必需能力。缺少权限时的启动限制、保护范围与回读、停止发单和交易所实际撤单的差异须明确定义；不能把同一账户的各产品可用保证金直接合并抵扣。

股票相关产品按 [开空与接入通道选择](23-stock-short-selling-access.md) 已选择的 USDT 股票永续细化：标的股票休市期间是否继续做市、参考价格失效时如何处理、资金费及保证金变化如何进入风险判断。平台可交易时段与策略获准运行时段分别表达，具体规则由本问题讨论，不由产品接入选择自动决定。

用户已要求跨国内 CTP 与境外 Binance 的自动策略，需覆盖节点间断连、一侧下单成功而另一侧失败、迟到/重复指令、各节点重启及重新接管时的归属校验。与 [跨市场策略协作问题](25-cross-market-strategy-budget.md) 对齐场景和可观察状态，具体交易处置由本问题决定。

用户进一步要求后台重连共享空间、确认同步后自动启动，不采用此前建议的人工启动作为默认恢复方案。需明确同步完成与交易状态核对的关系、恢复代次与旧指令隔离、哪些故障允许自动恢复，以及无法完成核对时的行为；索引相同不能未经证明视作订单、持仓和内存内容均一致。持仓、风控等关键模块失联要求急停，完整关键名单、作用范围、停止新单/撤单/减仓行为及执行路径待明确，不能把“急停”直接实现成进程退出。

后续已确认的恢复与急停边界以 [部署讨论 Q20–Q23](01-deployment-lifecycle.md) 为准：按依赖路径停新单并在通道可用时尝试撤相关挂单，不自动市价平仓；保留进程；依赖、共享版本/代次及外部订单持仓全部核对完成后自动恢复。本题不重复决定这些原则，继续细化关键模块名单、业务有效性及超时、撤单失败/未知状态、迟到指令拒绝、自动恢复流程与验收场景。

按 [领域模型讨论 Q28–Q30](06-market-domain-model.md)，未归属持仓仍计入实际风险，归属变更需显式留痕；各策略逻辑持仓可在实际净持仓为零时继续存在。因此策略关闭逻辑持仓的意图必须结合真实账户模式/可平数量转换为通道指令，不能直接套用平仓或 reduce-only。明确账户实际持仓、归属账与订单成交之间的核对不变量，以及外部交易、部分成交和归属转移的处理。

## Answer

2026-09-14：经 Q34–Q49 用户确认及 [订单通道语义研究](../research/order-channel-semantics.md)，采用以下订单执行契约。它约束行为、状态和恢复条件，不预选内存布局、持久化实现或网络协议；本轮没有执行交易或故障/性能测试。

### 日常操作与风险规则

| 触发 | 动作与恢复条件 |
| --- | --- |
| 用户主动停止策略 | 停止新单、尝试撤该策略挂单、保留持仓；重启后保持停止，直到用户再次启动。 |
| 手工撤销策略挂单 | 先暂停该策略在该合约上的发单，再撤选中订单；其他挂单不自动全撤，发单需用户显式恢复。 |
| 普通单笔/频率超限 | 拒绝该请求，不据此将整个系统停止。 |
| 累计亏损/回撤越线 | 急停对应范围并保持停止，直到用户明确恢复；指标回落和重启不自动解除。 |
| 可识别的同账户同合约自成交冲突 | 拒绝新单并提示冲突订单，不擅自撤其他策略或手工挂单；已验证的通道原生保护可配合使用。 |
| 关键依赖失效 | 按直接/间接依赖及共享原生保护范围暂停新单、尝试撤相关挂单，保留后台，不自动市价平仓；核对后自动恢复技术故障路径。 |

手工与自动交易均经过账户、策略组、合约三层后台风控；检查适用的单笔数量/金额、价格偏离、持仓与未成交订单合计风险占用、报撤频率及亏损/回撤限额。限额为配置，所需指标未知不按零风险放行；策略逻辑持仓不能代替实际账户风险。显式恢复只解除相应停止意愿，仍须通过当前权限、数据和风控检查。

关键依赖包括该路径使用的共享空间/执行授权、实际持仓、账户资金、订单成交状态、风控、行情及必要定价结果；可恢复交易证据的保存能力也是相关新单前置。界面和历史图表查询故障只限制相应功能，不等同于执行证据保存失败。关键依赖的业务有效性与网络心跳分别判断。

### 发单与状态

1. 手工操作与策略均提交带明确账户、合约、归属、方向、价格/数量及执行授权的交易意图。逻辑持仓操作按真实账户模式转换，不能将逻辑平仓直接当作通道平仓。
2. 发单前核对环境、产品权限、账户模式、参数/数据有效性、执行授权及停止状态；通过适用的账户/策略组/合约风控并保留风险占用，保存重启后可恢复的意图和标识证据，才允许通道提交。状态不明或保存失败不自动降级放行。
3. 区分交易意图、一次提交尝试、通道订单与成交记录的身份，关联环境、账户和产品作用域；标识和映射可恢复。共享空间发布完成、SDK 返回成功、通道受理和实际成交分别表达。
4. 用订单业务状态、撤改请求状态及核对状态分别表达事实，允许“部分成交＋撤单待确认”并存。交易回报、查询和本地证据交叉核对，成交去重记账；迟到/重复回报不得重复增加持仓或无依据回退已知累计成交。
5. 明确拒绝、撤余确认或成交等证据决定风险占用的转换/释放；结果未知时保留可能占用。请求超时、查无记录或客户编号可复用均不足以单独证明请求未执行；历史查询缺口不能靠重新下单消除。

### 撤改、部分成交与跨市场

- 撤单只是请求，确认前旧单仍可能成交。默认等待旧单已撤或全部成交，再按最新目标及实际成交量决定新单；原生改单仅按已验证的产品规则使用，批量请求逐单核对结果。
- 部分成交进入账户实际持仓与对应归属账，撤销余量不回滚成交。成交/账户视图暂时不同步时明确显示核对状态，并限制依赖不确定数据的新单。
- 跨市场机会关联各腿订单、成交和剩余敞口，不宣称两侧原子成交。一腿成交另一腿失败/断线时停止该次机会继续开仓，尝试撤余并告警，保留已成交仓位；自动补单/对冲仅在另有明确策略授权、限额与时限时执行。

### 停止、保护与恢复

- 用户主动停止、手工合约发单暂停、累计亏损/回撤停止均保留用户重新启用门槛。依赖故障恢复不覆盖这些停止原因；前端交易启用与后台策略运行分别表达。
- 关键依赖失效按依赖路径急停；共享原生保护会将同保护范围的路径纳入影响。停止新单、尝试撤相关挂单、保留后台核对，不自动市价平仓。
- 做市需要的原生断线保护须按真实账户/symbol/underlying范围验证、回读及续期；失败或部分续期不能视为全范围保护正常。状态、订单和执行授权都要通过恢复核对才能恢复相关新单。
- 需要原生断线保护但能力/权限尚未验证或不可用时，保留产品功能，不启动相关实盘做市。共享保护启用前明确展示其对其他策略和手工挂单的影响，由统一管理者维护；单策略不能关闭其他路径依赖的保护。其内任一路径关键故障触发整个保护范围暂停和撤单，保护恢复后再逐路径核对恢复；范围以外的独立路径继续运行。
- 重连后检查节点身份/代次、共享版本、关键依赖、通道订单/持仓、风险占用和保护状态。旧代次、过期或已撤销意图由执行端拒绝；重放记录用于恢复，不自动重复发送未知交易。核对缺口保持受限并说明原因。
- 首次或外部交易可核实但归属未知时进入未归属账；无法解释的状态差额继续核对，不静默覆盖策略归属。补齐证据且不存在人工/风险停止原因后，技术故障路径自动恢复。

### 配置与后续设计

限额、亏损/回撤统计口径、数据/心跳有效期、保护续期余量、指令期限和查询重试预算应显式配置并验证，数值不由本轮任意冻结。股票永续默认底层正常交易时段做市，其他时段由策略显式启用并验证价格有效性。

后端架构负责实现风险占用与可恢复证据的一致衔接、单写者/执行授权和消息去重；运行诊断负责有效性状态、时间阈值及告警；历史数据负责留存及盈亏/回撤口径。接入验收按 [订单通道研究](../research/order-channel-semantics.md) 覆盖版本、账户权限与失败场景，不以文档设计代替实测。

后续责任分别落在 [后端架构](08-backend-architecture.md)、[运行诊断](20-runtime-observability-alerts.md)、[历史数据契约](19-factor-history-contract.md)、[策略验证范围](16-strategy-validation-scope.md) 和 [架构验收路线](10-architecture-roadmap.md)。行情数据新鲜度、亏损统计和超时等配置须在实施前具有明确来源与验收值，不能用“可配置”替代行为验证。
