# 跨网络共享虚拟内存的实现语义与故障边界

研究日期：2026-09-14。范围为第一方资料的有界可行性研究；未实现、测量网络或选定架构。用户的统一插件拓扑、跨节点共享空间、同步后自动恢复、关键模块失联急停均保留。以下“候选”“推断”不等于用户决议。

## 已核实的概念边界

| 概念 | 能提供什么 | 不能单靠它提供什么 |
| --- | --- | --- |
| 同机共享内存 | Linux MAP_SHARED、Windows 文件映射允许本机进程访问同一底层区域 | 跨网络副本同步；业务记录完整发布和读写协调仍需协议 |
| 相同虚拟地址 | 各进程协商相同映射基址，满足地址空间条件时可行 | 相同数字不等于同一物理内存或一致内容；Windows 明确说明远程文件映射不保持跨机器一致性 |
| 软件 DSM | 在网络机器上实现共享内存抽象，可用页保护、缺页、复制/失效及同步协议 | 普通网络上无需传输的远程读取，或没有一致性协议的任意并发写 |
| RDMA | 显式向已授权远端内存执行读写；硬件 DMA 可以规避相应 CPU 缓冲区复制 | 普通 C++ 指针直接跨主机解引用、自动全局缓存一致性、应用事务提交 |
| Socket 零拷贝 | 某些发送路径规避用户态到内核的复制 | 所有路径均无复制、已抵达远端或小包必然更快 |

同机映射依据 [Linux mmap](https://www.man7.org/linux/man-pages/man2/mmap.2.html)。固定基址和远程文件一致性限制依据 [Microsoft MapViewOfFileEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffileex)：地址可能冲突，官方建议映射中保存偏移量以允许不同基址。推断：跨 Ubuntu/Windows 的共享数据还应明确字节布局、对齐、版本与对象生命周期，不能因基址相同就共享带进程私有指针的任意对象。

软件 DSM 有可行先例。Princeton 作者研究的软件共享虚拟内存在普通网络接口上实现 home-based 协议；论文说明页粒度引起 false sharing，缺页和同步会引入消息、差分处理开销，release consistency 在同步点协调可见性。论文证明的是方案存在及其特定实验，不是 Tyche 的广域网延迟承诺。[OSDI 1996 原论文](https://www.usenix.org/legacy/publications/library/proceedings/osdi96/full_papers/zhou/)

RDMA 操作明确包含 remote_addr 和 rkey；本地请求进入 work queue，并非 CPU 对远端指针执行普通 load/store。[rdma-core ibv_post_send](https://github.com/linux-rdma/rdma-core/blob/master/libibverbs/man/ibv_post_send.3) Linux 用户态 verbs 要求相应库、设备驱动及内存资源管理；文档描述注册区域固定内存页及锁页额度。[Linux userspace verbs](https://www.kernel.org/doc/html/latest/infiniband/user_verbs.html)

Linux MSG_ZEROCOPY 仅是规避复制的提示，允许回退；文档称一般超过约 10 KB 才有收益，完成通知表示可复用缓冲区，不能视为发送已完成。推断：行情和指令的小包应单独测量，不将“所有零拷贝”设成未经测量的性能替代指标。[Linux MSG_ZEROCOPY](https://www.kernel.org/doc/html/latest/networking/msg_zerocopy.html)

## 部署现实与零拷贝范围

Windows 有 NetworkDirect 用户态 RDMA 接口，依靠 RDMA 网卡；Ubuntu/Linux 可经 verbs 访问。两者不是同一平台 API。[Microsoft NetworkDirect](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/hh997033%28v%3Dws.11%29)、[Linux userspace verbs](https://www.kernel.org/doc/html/latest/infiniband/user_verbs.html)

RoCEv2 可经过 IP 三层路由，NVIDIA 文档也描述 Windows/Linux 的 IP-based RoCE 互通。这说明 RDMA 不限于一台机器或同一二层网段，不能反过来说任何国内/境外普通云主机都具备 RDMA。[NVIDIA RoCEv2](https://networking-docs.nvidia.com/winofdocumentation/55052000/rocev2)

推断与未验证项：尚无用户服务器型号、RNIC、驱动、云网络/虚拟化权限、跨境路由与拥塞条件证据，因此不能承诺该线路可用 RDMA 或端到端零 CPU 拷贝。即使 RDMA 可用，数据仍经过网卡和网络传输；对最新远端数据的同步读取、所有权转移或确认会受到网络延迟影响。具体 Linux/Windows 发行版和驱动支持应在硬件清单确定后实测。普通网络通路可以实现相同共享空间协议的传输，但与 RDMA 的复制次数和完成语义需分别说明。

建议将“零拷贝”拆成可验证边界（待决）：插件写入共享记录后本机其他插件直接读；跨机传输是否避免用户态暂存复制；接收后是否直接暴露完整记录视图。跨网络数据移动不可省略，发布状态、加密和设备路径也可能带来复制。

## 三种候选：均保持策略插件逻辑拓扑

下表为研究者按以上事实提出的设计候选，不是已存在的 Tyche 实现，也不替用户做选择。前两列的“连续”必须区分真实进程虚拟地址连续与逻辑地址连续。

| 候选 | 插件看到的空间和操作 | 本地/跨市场拓扑 | 主要代价或前提 |
| --- | --- | --- | --- |
| A：透明软件 DSM | 连续虚拟地址区，普通指针访问；运行时处理远端页、所有权和可见性；同步语义仍须明确 | 插件可保持相同读写结构，只改变数据归属和部署 | 最贴近透明指针目标；两平台缺页/保护适配、页失效及故障解除阻塞复杂；指针访问可隐含网络等待；多写竞争增加协议成本 |
| B：显式共享区域 + RDMA | 全局区域/偏移量标识，获取本地视图、写入并发布；传输由 RDMA 执行 | 相同插件 API/依赖图，传输适配隐藏位置差异 | 不自动满足普通指针透明访问；需要 RNIC/网络能力；提交标记、顺序、版本和多写仲裁仍由协议实现 |
| C：显式共享区域 + 普通网络复制 | 与 B 类似的连续逻辑区域和完整记录视图；网络适配复制/同步区域 | 同样可保持统一插件 API/依赖图，同机直接共享，异地复制 | 普通机器可研究实现；跨机并非自动端到端零拷贝；需网络同步和缓冲区生命周期管理 |

推断：B/C 可作为同一接口的两种传输后端，但只有用户接受显式空间接口时才满足目标；A 可以使用 RDMA 加速传输，RDMA 本身不替代 DSM。因此不能仅凭“采用 RDMA”就关闭透明性和一致性问题。

## 一致性、故障和自动恢复

1. **索引相同不是同步完成证明。** Raft 的日志匹配以 index 与 term 等条件为依据，提交、持久化和应用位置也是不同状态；客户端请求重试需要序号去重。[Raft 原论文，§5.3、§7、§8](https://raft.github.io/raft.pdf) 推断：Tyche 至少需定义区域身份、重启代次、数据版本/格式、权威来源、完整快照及应用进度；不能仅比较环形缓冲区游标。环绕和重启后复用索引可能指向不同记录。
2. **多写与一写多读不是同一个问题。** 推断：一写多读可将完整记录发布和每来源顺序局限在一个生产者；多节点修改同一持仓/额度需要冲突规则、所有权或协调协议。行情、指令和持仓是否同一种可见性规则仍待用户决定。不能把本机原子变量等同跨节点原子更新。
3. **网络故障不能保证被瞬时、无误判地发现。** 异步系统中的故障检测需考虑准确性和完整性，可能怀疑仍存活但通信迟缓的节点。[Chandra/Toueg 第一方研究](https://www.cs.cornell.edu/info/people/sam/FDpapers.html) 推断：需分别规定怀疑失联的超时、进入限制/急停的时间、恢复条件；心跳有效也不证明关键模块业务数据已更新。
4. **代次隔离必须由执行端检查。** Chubby 的 sequencer 交给资源服务器检查，以防旧锁持有者的迟到请求；锁延时是另一种更弱的缓解办法。[Google Chubby 原论文 §2.4](https://storage.googleapis.com/gweb-research2023-media/pubtools/4444.pdf) 推断：在 Tyche 里仅递增 epoch 不足以阻止旧节点继续下单，接收指令/执行报单的一端必须拒绝失效代次和撤销的授权；不能绕过该检查直接访问通道。
5. **内存同步不证明外部订单一致。** 推断：若通道已接收指令但回报在网络断开时丢失，所有节点共享同一旧内存仍无法确定订单是否存在。Raft 内部去重也不能自动覆盖外部交易场所副作用。恢复门槛需包括通道状态核对、未知结果消歧及重复指令处理；具体 CTP/Binance 路径由订单恢复票核实。
6. **故障隔离与急停动作分开。** 推断：非关键模块失联可失效对应视图、阻止依赖功能并保留其他模块；关键模块失联触发停止什么、哪些节点执行、已有订单怎样处置，需要独立规则。若停止动作只能经已断开的网络发送，则无法保证另一端收到，执行端须有本地失效检测/授权到期等机制。

可供讨论的自动恢复状态链（提案）：重新加入 → 校验身份/代次/布局 → 获取权威快照并补齐记录 → 完成外部订单与持仓核对 → 验证关键依赖及执行授权 → 自动启用。任何门槛未满足时停留在受限状态；这保留用户“同步后自动启动”，未改成手动启动，也未预选 Raft。

## 研究期间收到的用户确认

Q18：统一共享空间和访问接口即可，无需普通指针跨机器直接访问。Q19：采用完整版本显式发布。Q20：停止所有依赖失联关键模块的交易路径，无依赖策略继续。由主会话传入；正式决议由部署边界票保存。基于这些确认，候选 B/C 的接口形态符合用户要求，RDMA 或普通网络以及具体发布协议仍未选择。候选 A 保留作为比较依据。

## 需要人决策的边界

- 已确认统一空间和接口满足目标；仍需明确空间/区域身份及句柄生命周期。
- 已确认完整版本显式发布；多节点能否同时写同一区域及冲突规则待定。
- 已确认按依赖交易路径急停；急停包括停止新单、撤单、退出后台中的哪些动作待定。
- 自动恢复时外部状态未能消歧、关键依赖未就绪，是否保持停机直到门槛满足？
- 普通国内/境外服务器是否必须可用；专用 RDMA 硬件/网络可否作为必要条件；端到端零 CPU 拷贝是硬性约束还是需按数据路径验收的性能目标？

研究完成仅表示上述技术边界已有依据。接口透明性、发布边界和急停作用域已获上述用户确认；具体一致性、部署硬件、急停动作和自动恢复协议尚未定案，不应关闭对应架构决策。
