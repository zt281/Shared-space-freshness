# Tyche 回测系统设计草案

状态：讨论草案。完整历史回测后续规划、单期货至期权链的阶段选择，以及共用核心、隔离和验证门槛已确认；权威记录见[验证范围决议](../issues/16-strategy-validation-scope.md#answer)。其余具体回测模型设计仍为建议。

## 起点与目标

Tyche 当前处于架构规划阶段，没有可运行的回测引擎或测量基线。已有要求包括 C++ 策略、逐笔相关行情拟合、策略独立风险偏移、参数版本及可追溯订单风控。

建议建立事件驱动回测系统，以可复现的模拟交易评价策略在明确成交假设下的表现。首先证明时序、订单和账目正确，再评价模型现实性，最后优化性能。参考技能里的 hft_backtest 是另一项目的历史说明，其代码现状及性能数字未在本仓库核验，不能作为 Tyche 的实测结果。

## 三种运行用途

- 决策复现：输入记录的行情、回报及状态，解释原运行为何产生某项决策。若新策略生成了不同订单，不得继续将旧订单的成交回报绑定给新订单。
- 故障仿真：按脚本注入回报与故障，检查预期状态转移；不用于估计成交概率。
- 历史回测：行情来自历史数据，订单回报由模拟交易场所根据本次实际产生的订单生成，盈亏受声明的撮合与费用模型约束。

三者复用核心业务逻辑，通过输入、时钟和订单通道适配器区分的方向已确认，具体接口仍交由后端架构确定。

## 建议模块

| 模块 | 对外职责与内部约束 |
| --- | --- |
| 数据准备 | 校验行情及合约元数据、交易日、时间单位、缺口、累计量重置；输出版本化事件流，保留原始来源。 |
| 仿真运行器 | 管理虚拟时间、事件排序、启动状态和终止条件；相同输入、配置、种子与版本生成相同轨迹。 |
| 策略运行 | 仅接收当时可见的行情、回报与状态；调用 C++ 拟合、报价和风控逻辑，输出订单意图。 |
| 模拟交易场所 | 处理订单到达、撤单到达、价格优先、队列、可用流动性及回报；各模型在内部可替换。 |
| 账户账本 | 维护实际与策略归属持仓、现金、费用、风险占用、结算和估值，逐事件可对账。 |
| 记录与分析 | 记录订单因果链及模型版本，生成收益、库存风险、成交与敏感性报告；报告计算放在事件热路径之外。 |

共享账本及风控的策略放在同一次因果模拟中；独立参数组或独立实验才并行运行。逻辑模块不预先决定进程部署。

## 必须先固定的仿真契约

1. 时间：区分交易场所事件时间、策略可见时间、订单/撤单到达时间、成交时间与回报可见时间。缺少接收时间时使用显式延迟假设并标记，不能冒充实测。
2. 顺序：以事件时间、明确的同时间优先级和稳定序号调度；优先级属于版本化模型。不能让新订单消费其生成之前发生的历史成交。
3. 可见性：交易场所状态与策略已知状态分开。交易场所成交后、回报到达前，策略仍可能认为订单在场。不能提前发布成交或释放策略侧风险占用。
4. 延迟：分别声明行情、计算、报单、撤单与回报延迟；首先支持固定值，随后支持有依据的分布和固定随机种子。回测墙钟耗时不充当模拟延迟。
5. 订单：显式处理接受、在场、部分成交、全部成交、撤销、拒绝和到期；撤单请求不等于已撤销，结果未知是本地证据状态，不能替代场所订单状态。
6. 数量与价格：价格按整数 tick 比较，数量按合约单位处理；订单类型逐项支持。FOK 全成或不成，FAK 立即成交后撤掉余量；无法模拟的类型明确拒绝。
7. 连续运行：持仓、现金与适用挂单按声明规则跨休市和交易日延续。结束时对剩余持仓估值；不得通过清空状态隐藏风险或亏损。

时序示例：策略在 10 ms 看到行情，计算至 12 ms 后提交，订单在 15 ms 到达场所，16 ms 成交，18 ms 回报可见。该订单不能参与 15 ms 之前的成交分配；策略在 18 ms 之前不能读到该次成交。具体数值仅用于解释，非性能目标。

## 数据决定成交模型的可信范围

- 只有盘口快照时：快照间发生的成交与撤单不能完整恢复。成交量/VWAP 分配、队列减少归因均须作为假设；提供保守与不同假设场景比较，不能称为精确交易所重放。
- 有逐笔成交和盘口增量时：可细化价格上的成交量分配，仍须明确主动方向及撤单归属未知如何处理。
- 有逐订单数据时：才进一步考虑详细队列重建，仍需校验数据完整性和对应市场规则。

每次撮合维护同一事件/价格上的剩余流动性预算，多个本地订单共享消费，禁止各自重复使用整笔历史成交量。主动单按到达时可消费的对手价与深度成交，不能把限价直接当成交价。快照补量规则亦须显式定义，避免同一挂单深度被反复当成新增流动性。

建议首版采用小订单、无市场冲击假设，报告中声明历史行情不因模拟订单改变。对成交率敏感的做市策略同时报告队列和延迟敏感性；乐观场景不是收益保证或数学上界。

## 账目与报告

逐事件核对数量守恒、手续费、现金流、冻结占用、实际与归属持仓。按产品规则处理合约乘数、开平、资金费、结算及多币种；初版未覆盖的生命周期应限制测试区间或明确拒绝，不静默跳过。

报告至少包含已实现/未实现盈亏、费用、权益与回撤、库存与风险暴露、成交率、撤单率、订单在场时间和成交后价格变化。期权补充 Delta/Vega 等风险暴露，理论价及 Greeks 标明模型和输入版本。没有已接受的保证金模型时，不宣称得到准确保证金收益率或强平结果。

每次运行保留输入摘要、代码与模型版本、参数及初始状态、时间排序规则、随机种子和输出摘要。记录数据缺口及未覆盖能力。训练或调参区间与评估区间分离，不用测试区间选择参数后再作为独立表现报告。

## 建议实施顺序与验收

1. 写仿真契约，用人工构造的少量事件验证时间排序、可见性、撤单与成交交错。
2. 选择一个市场的一种线性合约，打通限价单、部分成交、撤单、手续费、剩余持仓估值和逐事件账目。
3. 加入队列与延迟模型、共享流动性预算、FAK/FOK（仅在范围需要时），建立精确预期事件轨迹。
4. 接真实历史样本，校验数据质量，比较不同撮合假设；条件允许时用实际订单轨迹校准，使用独立样本评估。
5. 扩展到期权链：相关行情逐笔拟合、共享拟合输入版本、策略独立风险偏移，以及期货对冲。定价参数契约沿用专门问题的最终决议。
6. 扩展跨市场、多账户及资金约束；最后增加批量参数实验、报告和界面。

每一步覆盖买卖对称、同价 FIFO（适用模型下）、部分成交、数量守恒、终态不可再成交、累计量重置、午夜与交易日切换、残余持仓和未来信息隔离。新引擎先以手算轨迹为基准；有旧版本后，对固定样本逐事件差分，模型变化单独版本化。

性能优化前记录数据规模、活动订单数、参数组合数、硬件、日志设置及峰值内存。简单全订单扫描约为 O(E×A)，E 为事件数、A 为活动订单数；事件调度堆通常为每次 O(log Q)，Q 为待处理事件数，均须由具体实现核实。使用分块输入和流式结果避免全量日志常驻内存。先测瓶颈，再采用紧凑记录、预分配和价格索引；优化后轨迹必须保持一致。若未来选择 Numba 原型，分别报告首次编译与预热后运行时间。
