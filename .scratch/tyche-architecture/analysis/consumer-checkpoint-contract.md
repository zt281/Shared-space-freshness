# 消费检查点与恢复契约访谈

Status: confirmed; experiment pending

本轮先通过 grill-with-docs 明确消费者提交与恢复边界，再用独立 prototype 验证。关联[后端架构问题](../issues/08-backend-architecture.md)；不关闭该问题，不将建议视为已接受决策。

## 已确认

2026-09-25，用户对 Q1、Q2 回答“All as recommended”：

- Q1：允许纯计算领先于持久检查点。若已保存至事件 100、内存已处理至 108，崩溃后可从一致检查点重算 101–108。处理状态与输入位置一致提交；允许重算，不允许丢失输入或重复累计效果。
- Q2：采用独立的交易证据保存边界。完整计算检查点可以滞后，但向通道提交前必须保存交易意图、身份、风险占用及必要恢复信息；恢复必须把重放计算关联到已有意图，避免重复发单。沿用[既有订单契约](../issues/07-order-risk-recovery.md)，不自动重发结果未知的交易。

2026-09-25，用户对 Q3–Q5 回答“All as recommended”：

- Q3：保留重建状态所需的确切输入版本、参数及计算版本。重放恢复历史状态，不提交历史订单。缺失证据时保持相关路径受限；核对及当前有效性检查通过后才恢复新交易。
- Q4：允许其他消费者在生产者保存完整计算检查点之前使用已发布结果，但结果必须具有稳定身份，并保留足以恢复该确切版本的证据。仅存在于易失内存中的结果不能支持交易动作；发布、可恢复和交易放行分别判断。
- Q5：以事件数和内存限制未保存工作量，按数量或经过时间触发保存。达到边界时暂停进一步计算，限制依赖新单，待保存追上；保存失败则保持相关路径受限直到恢复，仍尽可能提供撤单与核对。实验数值与生产限额分别确定。

2026-09-25，用户回答“All other as recommended”，确认 Q6、Q7 及整体契约：

- Q6：意图与原计算关联，身份跨重放保持。实际提交尝试之前持久标记可能已发送；崩溃后先核对，不自动重发。能证明从未尝试的旧意图在恢复时退役，新交易基于当前输入；重放不自动生成替代订单。
- Q7：停止意愿独立于计算检查点保存。立即实施停止，保存成功后才报告已持久记录。恢复使用最新停止及交易记录，不从旧计算检查点恢复交易权限。

## 原型形式

用户明确修改 Q8：不制作交互 HTML；使用 C++ 执行实验并检查结果是否满足要求。沿用现有原型的实际文件保存、进程崩溃及独立结果核对方式，保留原始证据。完整契约已确认。

实验覆盖未保存后缀重放、检查点前可恢复发布、提交窗口崩溃、事件数/内存上限与保存失败、较新停止记录、缺失/损坏恢复证据。比较同一合成计算在逐事件保存与有界合批保存下的结果、同步次数及延迟；实验参数不是生产选择，进程崩溃不是断电证明。

原型将保存在 `prototype/consumer-checkpoint-recovery` 分支的 `prototype-freshness/consumer-checkpoint/`。该问题保持独立于完整后端架构决议。

## 事实与原型边界

现有消费者逐事件保存结果与进度；恢复不继承交易放行权限。[现有恢复实验](../../../prototype-freshness/cpp/README.md)只验证有限进程崩溃场景。最新[组合实验](../../../prototype-freshness/network/REMOTE-COMBO.md)发现消费者逐事件检查点成为重压尾延迟的主要来源；不构成生产容量或断电恢复证明。
