# QUIC 可靠流与持久副本实验

本轮验证用户已选的两个边界：先用 MsQuic；远端先保存，再向当地策略发布。独立源进程通过真实 UDP/QUIC 向独立接收进程复制，第三个消费者进程以不同虚拟地址挂接远端共享区，并继续使用原有结果/进度检查点。实验不连接交易账户。

MsQuic v2.6.1 与其固定 QuicTLS 子模块已隔离构建；依赖和逐命令记录见[构建证据](evidence-msquic-build-wsl/README.md)。本轮为 WSL Linux 回环协议实验，不是物理双机、Windows 原生、跨境网络或容量验收。结果与复现身份见[运行证据](evidence-quic-wsl/README.md)。

## 数据路径与进度

```text
Space 权威日志：完整追加并确认保存 C
  → 按订阅从已提交日志取记录 → 编码帧 → QUIC 数据流
  → 回调有界借用 RECEIVE 缓冲 → 应用工作线程核验 R
  → 远端完整 pwrite → fdatasync 确认 D
  → 短共享锁发布 ring/head/Record，推进 V
  → 独立 DurableConsumer：保存结果+游标+控制状态，推进 A
```

正常路径满足 `A ≤ V ≤ D ≤ R ≤ C`。每条流各有进度，每个消费者各有 A；两个对象不构成跨对象事务。源端提交与本地策略许可不等待远端 D。`StreamSend` 成功和 `SEND_COMPLETE` 只决定传输接纳/发送缓冲回收，不是远端保存证明。本轮 `D/V` 对外报告在共享发布完成后一起推进，但同步门闩和第 3/4 崩溃点分别覆盖保存、共享发布的边界；没有用它们报告保存到可见的时间分布。

`ReadableSpace` 是 `Space` 与新 `ReplicaSpace` 的共同只读入口，含 `attachment/read/read_after`。策略和检查点代码不接触 socket、QUIC stream 或补读命令。本轮增加虚调用且保留共享 robust mutex、历史 `pread`、逐条检查点同步；没有把这条路径宣称为最终低延迟实现。

`ReplicaSpace` 是接收者唯一写入的本地副本。写日志与 `fdatasync` 在共享读锁之外；消费者只能读到已发布 head 以内的记录，不能因为文件已变长就读到待确认尾段。小环仅保留最近 8 条，更老历史从本地副本日志读取。恢复验证全部记录，完成同步后才整体安装恢复后的 ring/head，恢复期间保持受限。

## 固定实验协议

单个连接使用一条双向控制流和至多两条单向数据流。两个独立权威日志分别对应固定测试对象 101/102；固定证书身份绑定源节点 1、接收节点 2。对象与节点身份是实验夹具，尚不是生产全局日志标识、服务发现或动态授权协议。

所有帧采用 4 字节大端长度和大端 64 位字段，最大 32 个字段（260 字节含长度）。版本为 `0x5459515500000001`。接收处理拆帧、合帧、分散缓冲及半帧；不发送原生 C++ `Change` 的 96 字节布局。记录保留源 sequence/epoch/version/proof、三种业务时间、载荷和原 seal；不把网络接收时刻改成来源核验时间。

| 消息 | 固定字段（长度之后） | 用途 |
| --- | --- | --- |
| SUBSCRIBE | protocol, 1, g, mask, log1, log2, D1, D2, node2 | 请求完整依赖清单及最后确认保存的前缀 |
| BARRIER | protocol, 2, g, mask, log1, log2, C1, C2, epoch1, epoch2, node1 | 源端截取逐流屏障向量 |
| DATA | protocol, 3, g, flow, log, 13 个记录字段 | 从已提交源日志复制完整必需事件 |
| PROGRESS | protocol, 4, g, flow, log, R, D, V, node2 | 应用层副本进度；不代表消费者 A |

远端先核验身份、长度、布尔表示、时间范围、连续序号和校验值。相同记录重复抵达不再保存/累计；同序异内容锁存故障。发现序号缺口，先限制依赖，再自动提交新代次订阅，从最后 D 请求完整前缀。旧代次帧被忽略，不推进进度。记录 seal 是原实验的非密码学完整性检查；网络身份和完整性由 TLS 提供，seal 不承担对抗性认证。

控制和数据可能以不同顺序到达。BARRIER 校验不能要求其 C 大于当前 D，因为后来提交的数据可能先于较早的屏障抵达。它只要求屏障不低于本次请求起点；所有选中对象达到相应屏障、来源代次匹配后，才解除订阅补齐限制。此标志只表示补齐，消费者仍独立检查业务新鲜度、自己的 A、核对、稳定期和主动停止。

新增依赖完全重申 mask，并先从该对象已有 D 补齐。重建接收进程默认启动实验配置 mask=1；要恢复包含第二对象的配置，控制端重新指定 mask=3。没有把动态订阅配置持久化作为已经完成的能力。

这里补齐全部使用完整保留日志，没有快照截断/压缩、长日志保留额度、应用级请求 ID 协议、主机丢盘重建或跨节点写者仲裁。固定对象 IDs 不应直接复用为生产日志谱系，源日志替换/迁移和历史前缀证明仍需单独设计。

## 背压、认证与生命周期

回调不等待磁盘。默认单 pending RECEIVE 模式下复制 `QUIC_BUFFER` 描述符，返回 PENDING；工作线程在使用完缓冲后恰好调用一次 `StreamReceiveComplete`。借用字节以原子比较交换预留，包含排队及正在处理的内容。默认单 pending 模式来自稳定 API 的默认设置，不启用 preview multi-receive ABI。

实验上限：应用任务 64 个、借用接收字节 512 KiB、数据发送在途字节 4 KiB、含控制预留的总发送字节 8 KiB、进程生命周期最多 16 个连接和 64 条流。MsQuic stream 接收窗口设为 4 KiB、连接窗口 16 KiB，并关闭发送缓冲复制，使小规模实验可触发背压。达到发送上限后保留源日志中的下一序号，待发送缓冲归还后继续；没有无限堆积发送对象。接收任务或字节额度不足则关闭该连接，之后重新补齐。库内存、socket/内核内存与全进程 RSS 不受上述应用字节数完全约束，尚未做资源容量测量。

两端正常证书链校验开启，并对预加载的对端 leaf DER 做精确匹配；客户端校验 `127.0.0.1` 的证书 IP SAN。私有 CA 追加到 QuicTLS 默认信任路径，故仅设置 CA 文件不足以证明固定节点身份。本轮额外 pin 拒绝同 CA 的另一客户端证书；另验证缺少客户端证书和错误 CA 时不得发布数据。测试私钥只存在于临时目录，正常结束和测试失败路径均清理，不进入证据或 Git。

关闭 0-RTT/恢复票据、DATAGRAM 和 cancel-on-loss。Listener 传入回环地址；MsQuic 内部 UDP socket 可以是 wildcard，再按监听地址过滤，因此没有声称内核 socket 只绑定回环。未改防火墙或系统信任库。

连接/流对象在应用线程和回调仍可能引用时保留。正常退出先停止 listener、请求连接关闭，等 `SHUTDOWN_COMPLETE`、应用任务及借用/发送缓冲归还，再关闭句柄和 registration。连接掉线、流 reset 或半帧不会形成业务提交。重连由实验控制端显式触发；没有生产常驻 supervisor、自动网络重试与密钥轮换。

## 重启与指令限制

接收者持日志独占 lease，并用 PID、启动身份及 pidfd 核实旧进程退出；仅超时或拿到 lease 不授权接管。完整且校验一致的尾记录在恢复同步后继续交付，即使旧进程未确认保存/返回。半条尾原样保留并拒绝恢复；检测到保存失败或同序冲突时锁存受限，不自动截断或重试覆盖。

本地 `provider_generation` 与来源 epoch 分开。限制、订阅重协商和提供者恢复推进该代次；它不会改写源记录的身份/时间。消费者即使未读到短暂的 gap，也会根据代次变化重新核对、等待稳定期，并让旧 pending 意图失效。unknown 仍保留待真实通道核对，主动停止不被解除。这个本地代次仍依赖保留的共享区，不构成主机重启或异地执行权撤销证明。

## 源端提交的后续验证

现已增加[源端有界提交对照](../network/SOURCE-COMMIT.md)及第七组 `quic_source_commit_scenarios`。同一二进制通过 `TYCHE_QUIC_SOURCE_MODE=sync|worker|batch` 选择实验入口，默认仍为 `sync`；`worker`/`batch` 各日志一个写线程。`TYCHE_QUIC_SOURCE_CAPACITY` 为每日志待提交上限（1..64），`TYCHE_QUIC_SOURCE_WAIT_NS` 为合批窗口（batch 默认 2,000,000，worker 为 0）。这些是合成实验配置，未选为生产参数。后续构建、负载命令及失败记录以该报告为准。

## 构建与复现

在已装 C++20、CMake、Ninja、Python 3 和 OpenSSL 命令行的 Ubuntu WSL 中，先按[依赖说明](evidence-msquic-build-wsl/README.md)构建私有 MsQuic，然后从本目录执行：

```sh
python3 quic_validate.py debug
python3 quic_validate.py ubsan
```

脚本仅使用本原型源码、D 盘证据和 `/home/alan/.cache/tyche-prototypes/quic-20260919` 缓存；记录准确命令、源码快照、编译选项、二进制哈希、退出码及逐进程日志，不覆盖原运行。开启 CMake 的 `TYCHE_QUIC_PROTOTYPE` 才需要 MsQuic；原来的五组 CTest 继续可独立构建。第六组是 `quic_replication_scenarios`。

这轮没有性能计时验收：控制台和诊断文件会影响调度，策略是纯累计与模拟指令。核对/稳定期使用显式逻辑时刻测试；源/接收记录同属本机单调时钟，不能用于跨主机时间误差结论。慢接收的 150ms 是故障注入值，不是实测网络 RTT。MsQuic/QuicTLS 库为 Release，UBSan 仅覆盖我们编译的 C++ 原型。真实 CPU/RSS、协议排队分位数、批量副本落盘收益、跨流拥塞隔离、MTU/丢包/带宽及物理部署仍待后续实验。
