# C++ 本地共享内存新鲜度原型

问题：真实跨进程共享内存中，消费者能否只通过统一数据视图判断新鲜度，并在半次写入、过期、来源重启及持锁退出后正确限制操作？

这是可丢弃的 **Linux 同机原型**，不是正式后端。两个进程分别模拟业务发布者和策略/执行消费者；父进程同时驱动实验。业务记录经过真实 POSIX 共享内存，管道仅用于安排实验动作和等待完成，没有把业务快照通过管道传给消费者。

## 运行

需要 Linux、支持 C++20 的编译器、CMake ≥3.20 和 pthread。已验证环境：GCC 15.2.0、CMake 4.4.3。无需第三方依赖或账户。

在原型工作区根目录运行：

```bash
bash prototype-freshness/cpp/run.sh
```

脚本构建并运行 CTest 中的两组跨进程场景：`freshness_probe`（44 项快照/恢复检查）和 `ordered_probe`（38 项逐笔消费检查）。每次写入独立 `build/ctest-evidence-<随机值>/`，保留所有观察。若已有编译结果，也可运行：

```bash
prototype-freshness/cpp/build/freshness_probe /tmp/tyche-freshness-my-new-run
```

输出目录必须尚不存在，程序拒绝覆盖。`publisher.jsonl` 保存每次发布者操作及每次压力发布的完整状态；`consumer.jsonl` 保存每次读取；`results.jsonl` 保存场景断言；`summary.json` 保存统计。示例阈值为预警 700ms、失效 1000ms、稳定观察 200ms、指令期限 500ms，均不用于生产。

## 布局与实现

- `model.hpp`：记录与只读观察值的值类型、演示阈值。
- `space.hpp / space.cpp`：共享空间 module；私有共享布局、锁、完整发布与读取、损坏恢复。不可复制，不对正常调用方暴露可写共享记录。
- `consumer.hpp`：消费者恢复 module；私有停止/核对/稳定期状态、绑定消费者与恢复轮次的核对凭据、指令期限与代次检查。不依赖 POSIX 或网络。
- `experiment.hpp / faults.hpp`：实验进程调度、完整 JSONL 输出、受控内部故障 seam。正常发布经过共享空间 interface；只有撕裂写入、缺口、未知时间、场景重置使用故障入口。
- `main.cpp`：场景与行为断言，不改写共享布局或消费者内部标志。
- `ordered_consumer.hpp`：逐笔消费进度与恢复门槛；每个消费者单独持有进度，处理成功才确认。
- `ordered_main.cpp`：一个发布者、两个消费者的真实进程实验，控制管道不传业务事件。
- `CMakeLists.txt` / `run-scenarios.cmake`：构建与可重复场景入口。遵循仓库要求保留可执行行为检查，不建立生产测试框架。
- `.clang-format`：C++ 格式约定；编译启用常用警告并将警告视为错误。本环境未安装 clang-format，未声称格式器校验通过。
- `evidence-local-linux/`：首次普通构建运行的完整原始观察，25 项通过，5000 次发布/5000 次并发读取；读取观察到 2537 个不同版本，这个数字由调度决定。
- `OBSERVATIONS.md`：实验结论及证明范围。

共享区域用 `shm_open` 和 `MAP_SHARED` 创建，名字唯一且权限为 0600；创建后立即取消名字，映射由两个进程持有直到退出，不留下共享内存命名对象。当前通过 fork 继承映射，不验证独立启动时的发现/挂接或不同虚拟地址。

候选发布方式采用 `PTHREAD_PROCESS_SHARED` 的 robust mutex。完整记录的读写都在同一互斥范围内；来源先在私有草稿中准备，再完整发布。写入进程持锁退出时，下一个读者处理 `EOWNERDEAD`，先把区域标为损坏/不可用，再恢复锁的可使用性；**锁可用不等于数据可用**。新发布者完整快照和消费端核对、稳定期完成前不能恢复发单。

这项选择遵循 [Linux 跨进程互斥文档](https://man7.org/linux/man-pages/man3/pthread_mutexattr_getpshared.3.html) 与 [robust mutex 文档](https://man7.org/linux/man-pages/man3/pthread_mutexattr_setrobust.3.html)。它是验证语义的候选，不是无锁、零拷贝或低延迟架构承诺。消费者复制共享快照，不能称为端到端零拷贝。

## 边界

- 新鲜度按可控逻辑毫秒计算，未验证真实跨机时钟、传播或时限误差。来源业务核验与收到旧副本仍是注入动作，不是已实现网络协议。
- 只模拟一份业务依赖；尚未实现两市场合约、完整对冲账或两侧输入时间差判断。
- `freshness_probe` 读取最新完整快照，允许略过中间版本；5000 次快照观察不能证明逐笔必达。新增 `ordered_probe` 单独检查两消费者的逐笔完整性，见下文；这也不是生产事件系统已验收的声明。
- `Consumer` 的授权、稳定期、订单核对及提交结果是明确的场景状态。没有真实风控、订单、持久化恢复或账户连接。
- 文件记录是实验观察，不是生产可恢复交易证据系统。进程/主机全面重启、磁盘故障与永久保存尚未验收。
- 5000/5000 是并发完整性检查，不是容量曲线。注入的短暂等待和记录成本不能用于宣称 p99/p99.9 或吞吐达标。
- 不覆盖 Windows、跨机器虚拟共享空间或目标国内/境外部署；这些留在问题单中。

## 本轮 interface 契约

- 共享空间仍要求单一权威写入者，实验进程管道串行安排发布动作；interface 封装不等于已实现跨节点写入权限控制。
- `prepare / publish` 发布私有完整草稿；没有草稿、代次改变、重复发布、损坏或缺口时拒绝普通发布。`replace` 模拟来源完整快照，才可修复缺口/损坏。`verify` 模拟来源业务核验，不修复缺口。
- 消费者接收当前共享空间观察值。每次判断放行、创建/执行意图、接受核对结果都自行观察，不要求先调用 `observe`；缓存的有效标签也不能越过新鲜度期限。
- 观察值不是永久授权：本原型不能从旧拷贝获知读取之后的权威代次变化，也不保证快照读取与外部交易提交原子化。调用方须提供当前观察；生产执行端最终校验仍待实现。
- 核对开始时取得 `RecoveryTicket`，异步完成时原样交回。凭据绑定消费者身份、权威代次和恢复轮次；同代次再次失效也会使旧凭据失效。重复观察同一次失效不会无限产生新轮次。
- 数据重新有效即开始稳定观察，与核对并行。核对完成不重新计时；再次失效则重置。主动停止仅能显式解除，解除也不绕过其他恢复条件。
- 初始消费者仍按旧场景假定已完成启动核对；不代表生产启动可跳过核对。消费者身份计数只用于单线程实验进程，非跨进程持久身份。
- 快照消费者只能识别读到的失效与代次变化；`Consumer other` 仅检查凭据隔离。新增逐笔实验只记录完整业务发布、完整来源快照和业务核验，不是覆盖所有故障、代次和操作的生产事件协议；未观察到的短暂故障仍待进一步验证。
- 保留原有 25 项检查，新增 19 项 interface 与恢复场景，共 44 项；没有降低证据字段或原始记录粒度。首次 25 项历史证据保持不动，新运行写入新目录。

可另建 UBSan 构建进行检查：

```bash
cmake -S prototype-freshness/cpp -B prototype-freshness/cpp/build-architecture-ubsan -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_FLAGS="-fsanitize=undefined -fno-sanitize-recover=all -fno-omit-frame-pointer"
cmake --build prototype-freshness/cpp/build-architecture-ubsan --parallel 2
ctest --test-dir prototype-freshness/cpp/build-architecture-ubsan --output-on-failure --verbose
```

## 逐笔双消费者实验

```bash
prototype-freshness/cpp/build/ordered_probe /tmp/tyche-ordered-my-new-run
```

输出目录必须不存在。四个场景目录分别检查慢组追赶、必需记录缺失、公共记录容量耗尽、单消费者处理失败。各目录包含 `publisher.jsonl`、仅此实验使用的 `PROTOTYPE-events.bin`，以及两个消费者各自的 `events.jsonl`、`states.jsonl`、`views.jsonl`。消费者状态记录积压、进度、补读次数、恢复状态、模拟撤余/告警、指令结果和 Linux CPU/RSS 观察；原有快照记录字段不减少。

- 同一 `Space` 提供最新快照与有序记录；8 条共享缓冲、4 条积压阈值均为演示值。最新快照和有序记录在同一互斥范围内发布/读取，不增加策略可见的网络通道。
- 完整记录先写入本地实验文件并执行 `fdatasync`，成功后才发布序号及快照。滚动覆盖的是共享缓冲，已发布事件的完整记录不因消费者落后而删除。超出缓冲从同一 `Space` 补读，单批最多 8 条。
- 每个消费者从序号 1 开始，只有处理成功才推进自己的进度；检查顺序和记录校验。处理失败允许重试同一事件，**不是应用副作用恰好一次的保证**。消费进度只在进程内存中，不支持重启恢复。
- 超过示例积压阈值时，仅限制落后组并记录模拟撤余/告警。即使尚未达到阈值，只要仍有待处理必需事件，也不允许产生新指令；及时处理后无需额外恢复流程。
- 完整补齐、有效数据、核对与稳定观察全部满足后才可放行，主动停止必须显式解除。正常新事件及时处理不会重置稳定期；再次越过积压阈值或处理失败则重新受限。
- 读取缺失/损坏的必需记录时，不推进失败批次进度，并将该共享记录依赖标为故障，限制两个消费者。容量配额耗尽在写入路径拒绝发布，不让未保存事件出现在公开序号或快照中。
- 缺失场景有意截断**刚创建的实验日志**；容量场景采用可控记录数配额，不冒充操作系统磁盘写满测试。失败的公共记录不会通过替换快照或解除主动停止自动恢复；需要的实际修复流程尚未实现。

证明范围：同机 Linux、继承映射、确定性调度、单记录类型、有限合成事件。文件为本机构建的二进制结构，不是可移植格式；文件 I/O 在锁内，不能据此承诺慢组的性能隔离。消费者事件回调仅记录处理成功，没有真实交易副作用。未覆盖写日志与发布之间崩溃、独立启动挂接、跨机器、全量故障事件、重启恢复、生产容量或真实交易核对。完整逐条证据用于验证语义，不构成生产存储选型。
