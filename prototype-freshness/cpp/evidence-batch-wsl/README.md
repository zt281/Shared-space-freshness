# 有界批量提交的本机证据，2026-09-19

实验问题、锁顺序、失败/恢复规则和命令见 [BATCHED.md](../BATCHED.md)。原 `evidence-capacity-wsl` 基线没有改写。

确定性结论：批量写线程在同步门闩等待时，另一个独立进程成功读取旧完整版本及旧日志前缀，不能读取待提交尾；四条提议用一次同步确认，再整批共享发布。完整前缀/完整批次按既有规则恢复，半条尾保持拒绝。最终 Debug 和 UBSan 各通过 379 个既有检查＋120 个新增检查，共 499 个；这包括旧匿名 fork 实验。

性能结论受到明确限制：读锁等待变短，但端到端结果没有一致变好。逐事件检查点保存仍有成本；本机还观测到一次真实的替换失败和明显短时漂移，不能据此给出可持续容量、生产队列参数或尾部承诺。

## 检查点替换失败

首次 10 ms、1 消费者、200/s 档的发布者确认 400 条，但消费者在确认 245 条后报告 `durable consumption: replace complete checkpoint`。只读核验确认：旧检查点 cursor=246、revision=247（含初始化事件）恰好覆盖已经确认的前缀；完整的待替换文件 cursor=247、revision=248 保留，没有被提升为已提交结果。发布日志仍是 401 条完整记录。原始失败、暂存文件、逐项 CSV 和退出码都保留，详情见 [analysis/checkpoint-replacement-failure.json](analysis/checkpoint-replacement-failure.json)。

同二进制、同参数的唯一复验未再次触发该错误，但仅完成 250/400，不能称为通过性能验收。原实现没有保存 rename 的 errno，原因未定；没有自动重试、修复或降低持久化。后续目标存储验收需要带 errno 的失败证据。现有 harness 在消费成功后才填该事件的开始时间；失败尝试的确切开始时间未被捕获，不能补造。计划输入、成功前缀、错误和未完成数完整保留。

## 测量与平台边界

- Windows Ryzen 7 3700X 主机、Ubuntu WSL 8 vCPU/约 8 GB；无绑核、CPU/时钟/电源设置改动。仅测试 D 盘 NTFS，经 `/mnt/d` 的 9p/DrvFs 路径；不是 C 盘 VHD/ext4 对照，也不是跨网络能力验证。
- 单调同机时钟。延迟起点为预先固定的计划到达；Record 逻辑 tick 在实际提议生成时产生，不证明真实源数据年龄或交易就绪条件。
- batch 完成时间来自写线程在同步及共享发布后生成的逐项结果；`enqueue_returned_ns` 和稍后收集 future 的 `result_observed_ns` 单独保存。没有用入队吞吐冒充发布完成。
- 消费完成和检查点完成时间沿用 consume 返回上界；没有逐系统调用剖分。检查点逐事件同步、替换和目录同步不变。生产定价、500 资产、真实交易、网络及重启重放不在计时范围。
- 时间数组预先分配，所有进程结束计时后才统一写诊断文件；不含生产指标持久化热路径，进程崩溃会丢本轮尚未保存的测量。业务日志和检查点仍按同步规则保存。
- Guard 计数包括轮询等所有测量期共享锁获取，不是每事件一把锁；最大等待不能替代端到端分位数。批量等待阈值不是落盘时限。排空预算在操作之间检查，已进入的磁盘调用不可取消；唯一复验超出预算 15.741 ms 已保留。
- 队满后的最终受限状态有场景观察；失败 receipt 之前设置受限的顺序另经代码审查，未单独构造首个失败 future 的竞态复现。
- 历史同步入口、接管扫描和归档补读仍可能持共享 Guard 做文件 I/O。布局 3 拒绝旧 1/2，原型不支持原地升级。
