# 当前电脑的 QUIC 合成网络实验

最新一轮为[远端有界保存对照](REMOTE-COMMIT.md)：远端每日志有界保存队列与小批量同步，保留先保存后发布边界并对照突发负载。上一轮为[源端有界提交对照](SOURCE-COMMIT.md)。

后续已完成[分段计时与配对基线](STAGES.md)，将源端排队、同步保存、传输回调、消费检查点和控制器观测分开；下文保留原始两轮实验的条件与结果。

用户 Q10 确认没有两台目标主机，先在当前 Windows 电脑继续验证。实验运行于已有 Ubuntu WSL：两端 MsQuic 进程、两个独立共享区消费者，加一个只转发 UDP 数据报的 Python 进程。转发层注入延迟、抖动、丢弃和带宽限制；TLS、可靠流和重传仍由 MsQuic 提供。没有配置防火墙、qdisc、系统信任库或外部服务器，没有真实交易。

运行时源日志、副本和逐事件检查点放在当前 WSL 的私有 ext4 缓存中，结束后完整复制到 `evidence/`。这一选择用于避免把此前 D/DrvFs 的间歇 `rename EACCES` 直接混入网络实验，不表示生产存储已验收。所用 Debug 二进制的 SHA256 为 `14eb6f222839c694a8082dc0a05027877b57cb8cd353ec98a536d8d54da7dc54`，对应[QUIC 行为验证](../cpp/QUIC.md)中的最终 Debug 构建。

## 条件与记录

每档先完成两条依赖日志的订阅，再以固定绝对计划时刻输入 **40 条/秒，共 2 秒、80 条**，交替发给两个对象。源端输入线程不等上条提交才排下一条，迟到也不后移后续计划；保存每条原定时刻、实际交给控制管道的时刻、源提交答复、远端共享发布和消费检查点观测。输入结束后给最多 12 秒排空，未完成项继续留在计划表。初始化额外包含每对象一条记录，不混入 80 条计划输入。

每个消费者约每 20ms 发起一次完整前缀消费，逐事件保存原有 128 字节结果/进度检查点。延迟数字是**计划输入至观察到检查点完成的上界**，含控制管道、调度、磁盘、网络和轮询；不是交易所往返、tick-to-order、逐条内部处理时间或硬件时间戳。仅 80 个观测时最近秩 p99 等于最大值，不能据此验收生产尾分位数。

UDP 转发层每方向最多保留 64 KiB 数据报载荷，按 `UDP payload + 28` 字节计 IPv4/UDP 的序列化预算，再加单向延迟与均匀抖动；未包含 Ethernet、物理链路及隧道开销。随机丢弃发生在转发入队前，记录实际丢弃原因和每个包的调度/发送时刻；固定 RNG 种子不保证重复运行时 QUIC 会产生同样的包序列。拥塞、流量控制、内核/库缓冲和两条流共享的应用写盘线程仍会增加等待。

| 档位 | 每方向条件 |
| --- | --- |
| relay-baseline | 无注入延迟、丢弃或带宽限制；仍经过本机转发进程 |
| delay-and-jitter | 单向 40ms ±5ms，2 Mbit/s |
| loss-and-reordering | 单向 10ms ±8ms，1 Mbit/s，逐包 3% 丢弃概率 |
| bandwidth-limited | 单向 10ms ±2ms，32 kbit/s |
| temporary-blackout | 单向 5ms，2 Mbit/s；输入开始 350ms 后双向丢弃 1.5 秒 |

## 两轮结果

两轮都完成全部 400 条计划输入；独立解码确认每档两条源日志、副本和消费者检查点均准确达到 41 条（各含 1 条初始化）。没有漏计、重复累计或模拟外部指令。这个成功条件只检查在有限排空预算内最终补齐，**不表示数据在使用时一直有效或性能达标**。

| 档位 | 首轮输入窗口内完成 | 复验输入窗口内完成 | 复验最终完成 | 复验输入结束后排空 | 复验最大观测延迟 |
| --- | --- | --- | --- | --- | --- |
| 无注入基线 | 79/80 | 78/80 | 80/80 | 12.99ms | 63.32ms |
| 延迟/抖动 | 77/80 | 57/80 | 80/80 | 3,611.04ms | 3,686.04ms |
| 丢包/重排 | 78/80 | 18/80 | 80/80 | 6,046.61ms | 6,071.61ms |
| 带宽受限 | 30/80 | 10/80 | 80/80 | 11,550.77ms | 11,611.87ms |
| 短时中断 | 16/80 | 6/80 | 80/80 | 3,403.98ms | 3,803.98ms |

首轮 `quic-evidence-8678ce41d833` 与本轮 Windows 文件哈希审计有重叠，仅保留为探索性结果，不拿它的尾延迟排名。之后同代码、同二进制、同配置复验 `quic-evidence-3d65fe720839` 时没有并行运行本轮构建/审计/其他测试；没有排除操作系统、磁盘和用户其他任务的影响。结果仍明显漂移，因此不能把两次的差值归因于某一机制，也不能挑较快一次定生产参数。

复验的丢包档实际丢弃 14/407 个数据报并观测到 21 次同方向发送次序回退；中断档丢弃 35 个。未出现转发 socket 错误或 64 KiB 队满丢弃。实际调度也并不严格等于设定值：复验延迟档最大转发发送迟到约 176.28ms，带宽档约 380.86ms，分别在 `relay.jsonl` 留痕。不能把配置的 40ms 当成实测恒定单向延迟。

延迟、丢包、带宽和中断档分别记录 12、36、61、137 次过期消费者观察，过期观察下都保持禁止新意图。观察次数由轮询/处理速度决定，不是独立事件数；没有通过重传改变来源核验时间。最终补齐历史不会使已经过期的交易机会重新有效。

## 本轮说明了什么

32 kbit/s 档无法长期跟上本例的输入：当前每个 DATA 帧 148 字节，仅 40 条/秒的应用帧就需 47,360 bit/s，已超过该方向预算，尚未计 QUIC/UDP/IP 开销。这给出该具体编码与带宽预算的约束，不是多资产策略容量上限；输入窗口内观察到的 10/80 或 30/80 也不是稳态服务率。

现有证据包含源端提交答复 C、远端发布 V 和消费检查点观测 A。C 到 V 之间还混有传输、重传等待和远端保存，A 又包含本地保存及轮询；尚不能从本轮长尾确定是哪项主导。因此下一步先补接收、保存开始/结束、完整发布和实际消费完成的分段时间及 CPU/调度/队列资源记录，再在相同输入与持久化条件下比较窗口、批量和按所有者拆分工作线程。继续保留全部计划输入、超时项、原始证据和过期限制。

这轮使用两个合成对象和纯累计消费者，不包含 500 合约、20 策略实例、共享拟合、真实报价/风控/发单、生产完整指标保存或真实地域链路。不能据此宣称 1ms/5ms 目标、QUIC 的稳定最高吞吐、colo 必要性或某机房已满足要求。

## 复现与审计

先按 [C++ QUIC 说明](../cpp/QUIC.md)取得该可丢弃二进制，再在 Ubuntu WSL 运行：

```sh
python3 quic_network_probe.py \
  --worker /home/alan/.cache/tyche-prototypes/quic-20260919/validated-debug/quic_worker \
  --evidence-root /home/alan/.cache/tyche-prototypes/quic-20260919/network-evidence
```

结束后复制新证据目录至 `evidence/`，从本目录执行：

```sh
python3 network_audit.py evidence/quic-evidence-3d65fe720839
```

`network_audit.py` 独立重算每个计划输入的结果和窗口完成数，核对源 ABI 与大端副本编码、检查点累计/顺序摘要、未发单、退出码、真实丢弃/重排和转发调度迟到。`network-audit.json` 包含逐档结果与文件 SHA256；两轮原始数据都不覆盖。
