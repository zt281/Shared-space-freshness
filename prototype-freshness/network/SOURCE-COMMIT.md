# QUIC 源端有界提交对照

本轮回答：将已验证的本地批量提交接入 QUIC 源端后，能否在保留完整日志、保存后发布和失败限制的条件下减少排队及整轮延迟？这是当前 Windows/WSL 的有限原型实验，不是正式存储、网络或策略容量验收。

## 三个模式与共同边界

| 模式 | 源端执行方式 | 同步与发布 |
| --- | --- | --- |
| `sync` | 原应用线程调用 `Space::prepare/publish` | 每条同步，磁盘等待仍在共享锁内 |
| `worker` | 每条日志一个 `BatchPublisher` 写线程 | 每批仅一条；磁盘等待移出共享读锁 |
| `batch` | 与 `worker` 相同的两个写线程 | 最多 8 条、候选合批窗口 2ms，一次同步后发布完整批次 |

两个异步模式各日志最多 64 条待提交记录，包含队列和正在保存的记录；最多两个日志、128 个待答复命令。网络应用线程不等待 future，而是在原循环中检查最终回执，空闲轮询间隔仍最多约 1ms 的配置等待，加调度延迟。这些不是生产线程数、容量或延迟上限。

64 条上限限定尚未保存完成的输入；已完成但整次调用尚未答复的逐事件回执另计，合成控制接口每次调用最多 10,000 条。进程总内存还包括回执、传输、日志读缓存及旁路，完整字节预算不能仅由待写条数推出。

2ms 是合批收集窗口，不能限制前序写盘、排队和调度造成的等待；本轮平稳档提交队列也出现约 40.75ms 等待。每日志一线程仅用于两个对象的对照，不能直接外推成 500 个资产各建一条写线程。

`sync` 与 `worker` 的差别同时包括写线程布局及共享锁外写盘；不能把二者差值全部归因于线程。`worker` 与 `batch` 使用同一代码路径，仅改变每批上限和等待。远端仍逐条保存后发布，两个消费者仍逐事件同步保存结果/进度，消费触发间隔约 20ms；这几处均未优化。

源端接纳时固定序号、版本及载荷指纹，接纳不代表提交成功。应用线程只有取得保存并发布完成的最终回执才返回成功；成功回执包含原身份与确认时刻。队满或未知保存结果关闭包含该来源的复制连接，并锁定来源受限；已接纳前缀可继续保存，但不会因此清除输入缺口。未接纳的记录与尚未尝试的后缀明确区分。不得用高水位代替原身份查询，也不得自动重发未知调用。

控制管道只是合成调用入口。原身份的查证使用日志解码及已有共享空间历史读接口；本轮没有增加通用客户端幂等请求索引，也没有将易失的控制命令编号变成持久事务身份。

当前两个对象可能共享一条连接，故一个来源失败会同时限制该连接上的其他对象；这仍不是生产级故障隔离。重启沿用先确认旧实例退出、完整日志恢复、半条尾拒绝、检测到保存失败保持锁定。共享内存、磁盘格式和 QUIC 帧格式未改变。新增接口只是实验命令与诊断旁路。

三模式的合成记录统一使用命令进入源进程时的单调时钟作为模拟来源核验时刻，源端队列等待不再被重新生成的时刻掩盖；固定计划至入口的等待另行保存。此前分段实验在实际 prepare 时生成该时刻，故不能把新旧二进制的有效性观察直接做因果对照。这仍不是交易所时间、同步时钟误差或真实行情新鲜度验收。

## 故障与证据要求

新增独立进程检查覆盖两个异步模式的单次多事件调用、环形区回绕、消费者检查点重启，以及保存前门闩下的可见性。另覆盖容量 4 的队满、同步保存错误、源端七个崩溃位置。只有旧实例已退出才启动替代实例。独立审计重新解码 96 字节源记录、124 字节大端副本和 128 字节结果/进度检查点，并逐项核对回执的身份及先后关系。

代码复核增加了一项容量 1 的回归：两个日志各占一个尚未答复的命令槽后，第三个必需输入在总待答复上限处被拒绝。旧实现只返回错误、漏掉来源缺口标记；新测试在旧二进制上触发失败，修正后在拒绝答复之前同时锁定本地来源并限制相关复制连接，已接纳的两个调用继续正常排空。失败原始记录和修正后的验证均保留；初次 18 档测量使用修正前二进制，最终测量另行完整重跑，不混为同一构建。

首次完整 Release 回归保留一次失败：原慢接收测试先建立连接，再通过同步入口一次发布 200 条；源端约 5.8 秒未执行发送，连接在原有 5 秒空闲限时关闭。源端答复在断开之后到达，远端保持第 1 条且受限。该失败没有通过增加超时或重试掩盖。慢接收测试现在先保存 200 条再建立连接，单独验证接收背压；原同步批量命令阻塞网络应用线程的限制仍存在，不能宣称已被修复。两个场景的目的和证据分别保留。

## 负载方法

同一 Release 二进制、直接本机 QUIC、运行时日志位于 WSL ext4。每档交替输入两条对象日志，共 80 条，另各有一条初始化记录：平稳档 40 条/秒、2 秒；突发档平均 80 条/秒、1 秒，每 100ms 同时计划 8 条。迟到不后移计划，不等前一提交答复才安排下一条。最多再排空 12 秒，所有计划、拒绝、未完成和源回执均保留。

三轮按 `sync/worker/batch`、`worker/batch/sync`、`batch/sync/worker` 轮换顺序；各模式开启相同有界旁路。时间涵盖源端入口/应用排队/提交队列/同步/发布、QUIC 回调、远端保存及消费者检查点。批内每事件共享一次同步的时间区间，实际同步次数取发布器计数，不能数逐事件诊断标记来充当系统调用次数。

基准期间不并行本任务的构建、审计或其他实验；宿主及其他应用没有隔离。有限样本、顺序对照和 Windows/WSL 存储波动不能证明固定性能收益或生产尾分位数。仅 80 条时最近秩 p99 就是最大值。保留的旧 D/DrvFs 检查点替换 `EACCES` 未解决，ext4 条件不构成对其修复。

## 最终结果

最终 Release 与 UBSan 各 **7/7 CTest、790 项检查通过**：原本地 499、QUIC 124、新源端 14 个场景 167 项。构建、源码和原始测试分别保存在 [Release](evidence/source-commit-release-84328c8ffdd5/manifest.json) 与 [UBSan](evidence/source-commit-ubsan-af9c0afb9be4/manifest.json)。最终 worker SHA256：

- Release：`8913a3d8bafe32cb98c966eac8be95acbb824b3256723d08793dc3c30cdf4341`。
- UBSan：`2db20e278c077e279c407b3300076d4e55c0f6a2cbb2e881b40cd63f98e555a4`。

依赖仍为固定 MsQuic v2.6.1；库 SHA256 `10d88b8fcdc411952430525bdc08885ca3b09899e371f2924f7c6c41bc516b7a`。UBSan 检查自己的 C++，依赖仍为 Release 构建。两份最终源码快照与本轮代码一致。

[最终 18 档测量](evidence/source-commit-matrix-c3401bc1b4b2/manifest.json)的 **1,440/1,440 条全部完成**，每条均有完整阶段；[独立审计](evidence/source-commit-matrix-c3401bc1b4b2/stage-audit.json)核对源、远端、检查点及成功回执。无拒绝、未知结果或旁路溢出。初始化记录不计入下表的 80 条。

合批在三个突发档都将 80 次源同步降为 20 次，平均一次保存 4 条；事件没有合并丢弃。两个异步模式的源应用命令排队最大约 **0.234ms**，旧同步突发档最大约 **63.81–84.81ms**。这验证了释放网络应用线程和减少同步次数的机制，**没有得到固定的整轮收益**：第二轮 batch 最大值高于 worker 和 sync；一处等待减少后，远端串行保存和消费检查点仍会排队。

平稳输入下三种模式都进行了 80 次同步，2ms 窗口没有实际合批。三轮内部完成中位数范围为 sync **29.98–37.87ms**、worker **28.69–40.34ms**、batch **34.02–44.15ms**；batch 某次最大达到 **216.00ms**。低负载不能仅因启用“批量”就宣称更快。

最终最慢事件为 worker 突发第一轮的 **242.97ms**：源提交排队约 35.65ms，发送至完整回调约 22.92ms，回调至应用处理约 25.63ms，远端发布至消费开始约 109.20ms，检查点文件同步及目录同步各约 11.55/10.47ms。完整每事件分解保存在审计文件；不能相加不同阶段的分位数。控制器看到整次消费答复还晚约 76.54ms，该观察等待没有混入上述内部完成值。

最终样本源进程观测到 sync 13 个线程、两个异步模式各 15 个线程，RSS 约 15 MiB 量级（第一轮平稳档为 14,996 / 15,048 / 15,056 KiB，含诊断缓冲）。CPU tick 与上下文切换只是在有限采样跨度内的诊断，不是满载容量。未重新估计此实现的固定旁路开销。

## 保留的波动及下一步

修正总待答复上限之前另完成了 [240 条短试采](evidence/source-commit-prior-smoke-bada1696157d/stage-audit.json)和 [1,440 条完整对照](evidence/source-commit-prior-matrix-5aceb0ca1840/stage-audit.json)。它们使用 `7e38dc...` 二进制，均核对补齐成功，但前次对照最大内部完成曾达 **4,485.07ms**，且有 73 次过期状态观察；这些消费者均未放行。前次慢 batch 档两条发送数据流各观测到约 0.81/0.79 秒流控等待，发送至回调包含接收背压及库等待，不能当作纯网络传播时间。最终样本的过期观察为 0，也不能据此证明生产有效性。

这些前次数字不与最终构建混成分位数，也不归因于那个未在正常负载中触发的上限修正。当前宿主/WSL 存储与调度波动尚未隔离；最终较快并不能抹去旧长尾。各次单调时钟只在本次运行内关联，不跨运行拼接。原 [慢接收失败](evidence/source-commit-failed-release-6cadf8f0289b/manifest.json)和 [待答复上限失败](evidence/source-commit-red-completion-b2380e2dff2d/result.json)同样保留。

源端候选已具备机制证据，可以进入后续架构比较；2ms、8 条和每对象一线程尚未选为生产参数。下一轮优先把远端核验、保存和发布从同一应用任务中的等待分开，比较有界待保存队列及小批量保存，继续坚持远端保存后发布；消费者逐事件检查点先作为固定条件。若需要改变消费者提交/恢复边界，再通过 grill-with-docs 明确取舍。

本轮没有真实拟合、报价、风控、交易接口或生产指标保存负担；不是 tick-to-order 测量，不能验收 1ms/5ms 目标、500 合约/20 策略的上限，也不能据此决定 colo。目标主机、真实行情工作量和存储失效范围仍待原架构问题验证。
