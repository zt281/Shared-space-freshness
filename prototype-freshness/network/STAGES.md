# QUIC 分段计时与配对基线

后续源端接入与对照见[QUIC 源端有界提交对照](SOURCE-COMMIT.md)。下文保留本轮分段诊断时的代码状态和结论。

这是当前 Windows/Ubuntu WSL 上的可丢弃诊断，用于回答：既有持久化规则下，长尾积累在哪些阶段？不连接交易账户，不把纯累计消费者作为真实策略负载。

## 实现和测量边界

`diagnostic_trace.hpp` 提供可关闭的计时旁路。每个进程启动时预分配 65,536 条记录；多个线程取得不同槽位，运行时不写这些计时文件，所有写者结束后才输出。每条记录含进程/线程、日志身份、来源代次、序号、命令请求号及 `CLOCK_MONOTONIC` 纳秒时间。缓冲耗尽保留溢出计数，审计拒绝不完整记录。异常退出可能来不及输出旁路；原业务日志和故障证据继续适用。

源端、远端和两个消费者仍分别启动，使用原共享区、日志格式和检查点。没有调整持久化确认、逐笔交付、旧意图失效或恢复规则。当前 QUIC 源端调用的是逐条同步的 `Space::publish()`；此前已验证的 `BatchPublisher` 尚未接入这条路径。

记录以下边界：

```text
固定计划输入 → 源命令接纳 → 应用工作线程开始 → 源写入/同步/发布
  → StreamSend 调用 → 远端最后所需字节的 RECEIVE 回调 → 应用队列开始
  → 完整帧核验 R → 远端写入/同步 D → 完整共享状态 V
  → 消费处理 → 检查点创建/写入/文件同步/替换/目录同步 → 结果完成 A
  → 控制器观察到整次 consume 返回
```

R 与 RECEIVE 回调分开，跨回调的帧按流内字节区间关联。V 标记位于完整共享状态写入后、释放共享锁前，不能用它测出精确的解锁指令时刻。A 位于结果/进度保存且处理回调即将返回的位置，尚不是交易接口调用；控制器观察只是完成上界。`SEND_COMPLETE` 仅标记 MsQuic 归还缓冲，不能证明 R、D、V 或 A 已完成。

同一 WSL 中 Python `monotonic_ns` 与 C++ `CLOCK_MONOTONIC` 的进程启动及命令应答区间经过核对，每事件阶段按序相接，阶段和等于端到端观测。这个检查不证明跨主机时钟同步，也不证明纳秒级绝对精度。合成命令的业务记录仍在实际执行 prepare 时生成来源时间；预定到达与实际命令接纳时间只用于诊断，不把源队列中的等待伪装成真实市场数据年龄验证。

控制器仍每约 20ms 发起一次完整前缀消费，以保持对照条件；每个事件内部直接记录 A。一次消费可以处理多个事件，较早事件完成后仍须等待后续检查点，控制器才收到答复。因此观测误差可能明显超过 20ms。

## 条件和证据

- 同一 Release 构建，`-O3 -DNDEBUG`；worker SHA256 为 `b330a6794cb2d506197e43e85176e2cb924e689d841abdf15e1cffd1e3418e23`。
- 固定 MsQuic v2.6.1 / QuicTLS 依赖与上一轮一致。源码快照、编译命令、库/头文件哈希和日志见 [Release 验证](evidence/stage-build-release-09716b1416ac/manifest.json)与 [UBSan 验证](evidence/stage-build-ubsan-f0f9f14387ac/manifest.json)。两次六组 CTest 均通过：原有 499 项加 QUIC 124 项，共 623 项。UBSan 覆盖本原型，依赖库仍为原 Release 构建。
- 原有 Debug 数字不是这一轮的优化前基线。本轮没有实施性能优化。
- 每档两个对象、两个消费者，固定合计 40 条/秒、2 秒、80 条输入，额外初始化每对象一条；迟到不移动后续计划，最多另留 12 秒排空。
- 三种路径为直接 QUIC 回环、无扰动 UDP 转发、单向 40ms ±5ms 且每方向 2Mbit/s 的转发。后者没有主动注入丢包；抖动仍可能引起重排。
- 三轮，每轮逐路径配对关闭/开启旁路，第二轮反转开关顺序，共 18 档、1,440 条。源/副本/检查点逐字节审计一致，全部最终完成，其中九档 720 条有完整内部阶段记录。
- 首轮启动时上一项负向审计的结束回执尚未取得，保留为探索性记录；后两轮共 960 条用于主要比较，期间没有运行本轮其他构建、审计或测试。宿主系统和用户其他活动未隔离。
- 运行日志及检查点在 WSL ext4 VHD 内，结束后复制到 Windows 仓库；复制后的文件哈希逐项核对。C 盘当时可用约 28.5 GB，D 盘约 2.85 TB；未以 guest 虚拟容量代替宿主容量。
- 转发器的包调度逻辑与上一轮相同，本轮把包记录放在有界内存，停止后再保存。因此不能将两轮差异全部归于 Release 构建或 QUIC。

完整记录见 [配对矩阵](evidence/stage-matrix-c141aa16256a/manifest.json)和[独立审计](evidence/stage-matrix-c141aa16256a/stage-audit.json)。[首次试跑](evidence/stage-smoke-b1ee15402189/manifest.json)另保留 80 条；[溢出负向实验](evidence/stage-overflow-e78a98805296/manifest.json)把每进程缓冲压至 8 条，业务 80 条仍完成，但普通旁路审计拒绝全部四份不完整记录，不能算作性能样本。归档索引见 [stage-archive-index.json](evidence/stage-archive-index.json)。

## 结果：保存和排队能够形成秒级长尾

下表使用带计时档的**计划输入到内部 A**，不混入控制器最后看到答复的时间。每档只有 80 个样本，最近秩 p99 等于最大值；下表采用最大值名称，不将它作为生产尾分位数保证。

| 轮次 | 路径 | 输入窗口内内部完成 | 内部完成中位数 | 内部完成最大值 |
| --- | --- | --- | --- | --- |
| 1，探索 | 直接回环 | 30/80 | 1,673.81ms | 2,346.51ms |
| 1，探索 | 无扰动转发 | 54/80 | 564.80ms | 1,429.52ms |
| 1，探索 | 延迟档 | 78/80 | 78.26ms | 106.96ms |
| 2 | 直接回环 | 79/80 | 45.53ms | 64.07ms |
| 2 | 无扰动转发 | 79/80 | 44.28ms | 64.94ms |
| 2 | 延迟档 | 77/80 | 80.58ms | 101.64ms |
| 3 | 直接回环 | 27/80 | 1,858.54ms | 3,374.55ms |
| 3 | 无扰动转发 | 54/80 | 503.49ms | 917.49ms |
| 3 | 延迟档 | 78/80 | 81.49ms | 116.83ms |

直接回环第三轮最慢事件的内部完成耗时约 **3,374.55ms**，其中源端命令接纳后等待应用工作线程约 **2,647.13ms**，远端完整发布至开始处理该事件约 **426.70ms**；发送至接收回调不足 1ms。这一条事件本身的源端同步约 65.21ms，源队列等待还包含前面其他事件的保存。不能只看当前事件的一次同步就忽略积压。

| 直接回环的阶段 | 第二轮中位数 | 第三轮中位数 |
| --- | --- | --- |
| 源端 `fdatasync` | 6.75ms | 51.87ms |
| 远端 `fdatasync` | 8.77ms | 50.84ms |
| 消费检查点文件 `fdatasync` | 7.94ms | 54.38ms |
| 消费检查点目录 `fsync` | 10.43ms | 51.52ms |
| 应用发送至远端最后字节回调 | 0.39ms | 0.39ms |
| 远端发布至消费开始 | 10.44ms | 235.02ms |

这些是分别计算的阶段分位数，不能相加得到端到端分位数。每事件的真实分解在审计文件中保留，可以逐项相加。同步调用的墙钟时间包含等待及可能的调度停顿，不是物理盘纯服务时间。

源端第三轮应用任务队列最大观测深度为 48，任务最长排队约 2,712.62ms；上限仍为 64。远端工作队列深度最高为 2，但其中任务可因前序保存等待约 103.59ms。消费者既要等轮询，也会等待同一次消费中更早事件的逐条检查点。

三个带计时延迟档的应用发送至接收回调中位数约 **42.48–42.64ms**，与注入路径同一数量级；这段仍含 MsQuic、TLS、内核和应用回调调度，并非真实跨境链路测量。直接回环主要长尾没有出现在这段。探索轮某个事件从内部 A 到控制器观察还多等约 845.31ms，说明上轮只有控制器观测无法准确分段。

## 观测开销和资源限制

关闭/开启旁路的尾延迟差值不稳定，不能报告一个可信的固定开销百分比。第二轮直接回环的观测中位数分别约 46.96ms / 45.71ms；第三轮则约 46.93ms / 1,964.51ms，且关闭旁路也出现过秒级长尾。顺序对照不能排除随运行状态变化的影响，更不能据开启计时更快就宣称“负开销”。

资源每约 100ms 采一次，保留进程/线程 CPU tick、上下文切换、RSS、I/O 和 schedstat 原值。第二轮直接回环，源进程开启/关闭时最大采样 RSS 为 14,964 / 9,844 KiB，差值约为预分配缓冲大小。第三轮约 5.46 秒的资源观测中，源端所观察线程的 CPU tick 增量为 9，系统每秒 100 tick；这是有限采样区间内的累计量，不是生产 CPU 容量测量。计时缓冲以外的库内存归入进程 RSS，不能给出精确的库内存分类。

本机 `kernel.sched_schedstats=0`，所以不能把 schedstat 中的零等待解释为操作系统没有调度延迟。未采集宿主 ETW 或设备级队列证据，尚不能确定同步时间波动源于哪个物理盘、宿主文件活动或调度机制。之前 D/DrvFs 的 `EACCES` 也仍未解决。

MsQuic 统计仅在输入前、全部计划命令已写入后、排空后查询；每次 `GetParam` 的调用区间独立记录，它会向库工作线程排队并同步等待。当前句柄在应用线程退出之后才关闭，查询不跨越应用锁。仅使用稳定的 `QUIC_PARAM_CONN_STATISTICS_V2` 和 `QUIC_PARAM_STREAM_STATISTICS`：

- RTT 字段为微秒，取样时的平滑 RTT 不是某个业务事件的耗时。
- `SendSuspectedLostPackets` / `SendSpuriousLostPackets` 是库的丢失判断；稳定字段没有可直接当作实际重传次数的计数。
- `ConnBlockedBySchedulingUs` 是库发送调度等待，不是 Linux runnable delay；`StreamBlockedByAppUs` 也包括应用暂无数据的正常空闲。
- 各种 blocked 时间可能重叠，连接等待还会出现在多条流上，不得相加或跨流求和。
- 慢直接回环的源端数据流没有增加发送流控或拥塞等待；接收端控制流出现约 0.38–0.44 秒的流控等待，不能把它当作数据帧传输耗时或独立根因。

上述语义依据为固定版本的 [msquic.h](https://github.com/microsoft/msquic/blob/v2.6.1/src/inc/msquic.h)、[GetParam 实现](https://github.com/microsoft/msquic/blob/v2.6.1/src/core/api.c)、[流统计实现](https://github.com/microsoft/msquic/blob/v2.6.1/src/core/stream.c)及[丢失检测](https://github.com/microsoft/msquic/blob/v2.6.1/src/core/loss_detection.c)，本轮按本地相同版本源码核对。

## 本轮结论与下一项实验

已找到长尾累积的位置：逐条同步保存造成的源端任务排队，以及远端保存和消费检查点等待。当前证据支持先改善保存与排队布局；它没有证明存储设备的最终根因，也没有测出多资产生产上限。

**下一项只比较将已有 `BatchPublisher` 接入 QUIC 源端。** 用户此前已接受有界批量、确认保存后发布；当前网络源端还未使用该实现。比较时保留消费者逐事件检查点与远端保存顺序，并把“移到专用写线程”和“合批”拆成可辨认的对照，防止把多种改变混成一个收益数字。保存完成前仍不得推进发布或成功答复，必需事件和全部明细仍保留。具体批次与等待值仅是实验参数，收益及参数尚未验证。

源端改善后仍可能受远端同步、消费者逐事件文件/目录同步及 20ms 触发限制。若下一步要改变消费者的日志/检查点恢复方式，应单独通过 grill-with-docs 讨论，不用这份诊断默许新的提交契约。真实拟合、报价、风控、完整生产指标保存及目标主机验证仍在后续。

## 复现

在已有隔离 MsQuic 依赖环境内，从本目录运行：

```sh
python3 stage_validate.py release
python3 stage_probe.py --worker /home/alan/.cache/tyche-prototypes/quic-20260919/stage-release/quic_worker \
  --evidence-root /home/alan/.cache/tyche-prototypes/quic-20260919/stage-network-evidence --mode smoke
python3 stage_probe.py --worker /home/alan/.cache/tyche-prototypes/quic-20260919/stage-release/quic_worker \
  --evidence-root /home/alan/.cache/tyche-prototypes/quic-20260919/stage-network-evidence --mode matrix
python3 stage_audit.py /absolute/path/to/new/quic-evidence-directory
python3 stage_validate.py ubsan
```

命令必须逐一等到退出；基准运行期间不并行构建、审计或其他测试。`stage_probe.py --mode overflow` 生成明确不完整的旁路证据，随后以 `stage_audit.py <目录> --expect-overflow` 验证普通审计会拒绝它。归档脚本 `archive_stage_evidence.py` 固定了本轮运行身份且拒绝覆盖；新运行应使用新的归档清单。私有测试证书在临时目录生成，结束后删除，只归档公开证书。
